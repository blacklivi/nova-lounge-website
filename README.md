# NOVA — сайт сети кафе, Минск

Отдельный проект `blacklivi/nova-lounge-website` → Cloudflare Worker `nova-lounge-demo`.

## Ссылки
- Сайт: https://nova-lounge-demo.blacklivi-olx.workers.dev/
- События: https://nova-lounge-demo.blacklivi-olx.workers.dev/events
- Редактор: https://nova-lounge-demo.blacklivi-olx.workers.dev/admin

## Архитектура
- `public/` — адаптивный интерфейс, события, редактор и статические фотографии;
- `src/index.js` — защищённый API редактора, загрузка изображений;
- `D1 DB` `nova-content-db` — текстовые поля и анонсы;
- `R2 MEDIA` `nova-website-media` — загруженные изображения;
- `ADMIN_PASSWORD`, `ADMIN_SIGNING_KEY` — только Cloudflare Secrets, **не хранить в Git**.

Редактирование текстов и событий в `/admin` применяется сразу, без GitHub deploy. Изменение верстки/программного кода публикуется через коммит в GitHub `main` → Cloudflare Builds. Доступ в `/admin` требует отдельного пароля.

## Публикация

```
npm install
npm run check
npx wrangler deploy
```

Гостевой сайт использует опубликованные анонсы и сохраняет заявки на бронирование в D1. Заявка не является подтверждённой бронью до ответа сотрудника.

**Перед полноценным запуском:** проверить актуальность телефонов и времени работы, подтвердить оригинальность фотографий, подключить официальный домен. Технический адрес `workers.dev` исключён из индексации; это сделано намеренно. Не обещать автоматического подтверждения бронирования: Telegram пока не подключён; сотрудники обрабатывают поступающие заявки вручную.

## Контент и события
- Анонсы с `published=true` появляются в `/events`.
- Будущие сортируются по времени проведения (первый по времени — на главной).
- Прошедшие автоматически оказываются в архиве страницы `/events`.
- Неопубликованные объявления не видны посетителям.
- Время мероприятия вводится в часовом поясе **Минска (UTC+3)**.

## Важное
- Не подключать этот Worker к D1/R2 AVE.
- Секреты не записывать в GitHub и не публиковать в README.
- Изображения и тексты через CMS не требуют правок GitHub.
- Схема таблиц в `migrations/0001_content.sql` (уже применена на отдельной базе NOVA).

## Бронирования / RESERVED

- Для гостей: кнопки «Забронировать стол» отправляют реальные заявки через `POST /api/reservations`, после успешного сохранения в D1 отображается сообщение о получении заявки. Бронь требует подтверждения администратором.
- Для сотрудников: отдельная служебная страница `/reserved`. Логин `owner` + действующий пароль редактора NOVA (или секрет `RESERVATIONS_PASSWORD`) — владелец с доступом ко всем заведениям и кнопке «Пользователи».
- Владелец в /reserved создаёт персональные учётные записи с логином, длинным паролем (12+ символов), конкретным заведением и ролью:
  - `manager` — видит и меняет статусы бронирований **только своего** заведения;
  - `viewer` — видит бронирования **только своего** заведения, не меняет статусы;
  - `owner` — единственная привилегированная роль, доступна только по Cloudflare-секрету, не создаётся как обычный пользователь.
- Сервер независимо от параметров браузера проверяет роль и заведение в D1 при **каждом** запросе. Фильтры списка, подсчёт заявок и SQL UPDATE используют одну и ту же область доступа. Чужой ID брони возвращает 404; endpoint удаления бронирований отсутствует.
- Пароли персонала хранятся как PBKDF2-SHA256 с индивидуальной солью и серверным секретом; действующие сессии завершаются при смене роли, заведения, пароля или отключении пользователя. Пароли никогда не отображаются сотрудникам после создания. Не сообщайте персоналу пароль `owner` или пароль сайта.
- Сессии `/reserved` независимы от `/admin` и ограничены 8 часами. Обновление до ролевой системы завершает старые сессии RESERVED — владельцу потребуется повторно войти.
- Новый визуальный редактор страниц в `/admin` сохранён; старый редактор и его клиентская логика удалены. Редактор афиш продолжает работать.
- Миграция `migrations/0005_reservation_users.sql` создаёт `reservation_users`, `reservation_sessions`, `reservation_staff_audit` и колонку `reservation_audit.actor` (уже применена к production и preview D1). Начальных аккаунтов сотрудников нет — создайте их через владельца.

- Для отдельного пароля: в Cloudflare Workers → `nova-lounge-demo` → Settings → Variables and Secrets добавить секрет `RESERVATIONS_PASSWORD`. Он переопределит общий пароль администратора только для `/reserved`.
- Таблицы: `migrations/0003_reservations.sql` применить к production `nova-content-db` и preview `nova-content-preview-db`.
- Запись: заведение `zyb/pob/east`, дата/время Минска, число гостей, имя, телефон, комментарий, статус и согласие. Статусы меняются в `/reserved`, история изменений записывается в `reservation_audit`.
- Доступ к персональным данным: только после авторизации сотрудников. Не включать их в публичные ответы API, клиентские логи или кэш. Сотрудникам необходима организационная процедура обработки персональных данных и ограничения доступа.
- Telegram ещё не подключён, но в каждой записи уже есть `venue` и `telegram_sent_at`. До интеграции персоналу необходимо проверять `/reserved` вручную.

### Исправление создания сотрудников (ноябрь 2026)
Cloudflare Workers отклоняет PBKDF2 с количеством итераций более 100000. При попытке создать сотрудника прежние 160000 итераций вызывали HTTP 500. Используется 100000 итераций с индивидуальной солью и серверным секретом; пароли по-прежнему не хранятся открыто. Автоматическая проверка запрещает возвращать несовместимую настройку.
